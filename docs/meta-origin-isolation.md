# Storefront and commerce origin isolation

The application uses two root documents and one commerce backend. The public root is `app/(shop)/layout.tsx`; private commerce, authentication and administration are below `app/(private-commerce)/layout.tsx`. There is no common `app/layout.tsx`. Shared `DocumentFrame` is a markup component rendered independently by each root, not a persistent parent layout.

## Browser boundary

Set `STOREFRONT_ORIGIN` and `COMMERCE_ORIGIN` to distinct HTTPS origins with distinct hostnames. Set matching `NEXT_PUBLIC_STOREFRONT_ORIGIN` and `NEXT_PUBLIC_COMMERCE_ORIGIN` at build time. Keep `AUTH_URL`, `SITE_URL` and `NEXT_PUBLIC_SITE_URL` on the retained commerce origin for this release: the shared site URL helper also creates SSLCommerz callbacks and browser redirects. Moving it to the catalog requires a separate reviewed change. Set `AIRWALLEX_RETURN_URL` explicitly to commerce. Port-only separation is rejected because host-only cookies do not use a port boundary. Development permits distinct loopback names such as `catalog.localhost` and `commerce.localhost`; production rejects HTTP. Deployment prerequisites and the unresolved apex/www compatibility blocker are in [the deployment runbook](deployment-runbook.md).

Until both origin configuration and migration readiness are established, tracking remains disabled. An absent configuration keeps the legacy commerce journey functional on one origin. A document split on that origin is never represented as storage or authenticated-API isolation.

The public root provides an explicit anonymous session view and an empty ephemeral catalog view store. It never mounts `SessionProvider`, `StoreHydrator`, private reducers or personal navbar data. It does not read the private cart or wishlist. Search input, review composition, contact, cart, checkout and account actions live on commerce. Public catalog controls navigate with public product, variant and quantity selections only.

Public cart/wishlist actions open the commerce shopping handoff. That page rechecks the product and asks the customer to confirm before any mutation, preventing an arbitrary cross-origin GET from modifying their cart. Registered mutations use the existing authorized server APIs; guest mutation re-fetches current variant stock and price before persisting. Checkout still revalidates pricing and stock transactionally. Buy now goes directly to commerce checkout and does not clear the existing cart. Purchased cart lines, account login merges and scoped order cookies retain their existing behavior.

Public navigation uses full document loads, including changes between allowed and denied public query contexts. Public catalog pagination replaces the document before displaying the next result set. Related-product expansion reloads with `related=all`, which remains untracked unless separately approved. Initial asynchronous review content carries a pending marker, preventing SDK loading until the actual content is available for policy validation. Public language choice uses an anonymous endpoint; commerce language choice can still update the account profile. Locale prefixes and historical slug redirects remain unchanged.

The current public product option and quantity can recover from a policy-driven clean reload through a single tab-local record that expires after ten minutes. It contains only the public product/variant IDs and quantity, with no prices, names, customer data, full cart or browsing-history list. The server-rendered document supplies validated navigation origins; stale public build variables cannot replace these destinations. All hydrated public catalog records, variants, images, related products and navigation categories are represented in public snapshots for policy fingerprinting, including initially hidden related records. Multi-slide autoplay banners carry a persistent mutable-context denial marker. They retain their presentation behavior, but the SDK remains unavailable on that document until the banner configuration is static and the resulting context is separately reviewed.

## Host and API enforcement

The proxy matches pages, APIs and assets. It rejects unrecognized hosts when isolation is configured. Private pages requested on storefront redirect to commerce before rendering. The storefront only exposes an explicit GET allowlist for anonymous product/category/brand/manufacturer/review/catalog APIs plus consent, policy and anonymous locale endpoints. It removes session, scoped guest-order and authorization credentials before forwarding public reads. Public APIs with optional administrative projections therefore receive no account identity.

Commerce rejects cross-origin private API requests. Provider callbacks retain their existing authentication and verification, including SSLCommerz browser callbacks, rather than being treated as customer API requests. No credentialed CORS is added. Existing checkout/auth origin checks stay in force. Host-only auth and guest cookies have no `Domain` attribute. Both documents use `no-referrer`; private CSP excludes Meta scripts, images and connections while allowing the payment providers. The reverse proxy must overwrite forwarding headers, reject unknown hosts, expose no private APIs under the storefront host and log only a bounded route class and status, never raw paths, order IDs, queries, cookies, referrers or IPs. Existing protected payment and order database audit records remain separate first-party business records. See `deploy/nginx/surfaces.conf.example`.

## Migration before tracking

Prefer retaining the existing untracked hostname as `COMMERCE_ORIGIN`. Existing sessions, guest order cookies and local carts then stay on their original origin; the new storefront receives no private storage. Keep old receipt links served by commerce, and keep tracking disabled on that hostname permanently. The public handoff appends a selection to that existing private cart only after confirmation.

If commerce must move, complete a separate untracked migration before setting `TRACKING_ISOLATION_READY=true`: retain the legacy host for existing guest receipts, ask account owners to sign in on the new host, and provide an explicit minimal cart selection export/import. Revalidate every imported variant and quantity through the commerce APIs. Never copy authentication tokens, guest order bearer cookies, addresses, order snapshots or entire local storage through query strings or cross-origin messaging. Never widen cookie Domain. Do not enable the storefront on a hostname that retains historical commerce storage or parent-domain private cookies. Keep readiness false until this is verified manually.

The legacy-host migration is an infrastructure prerequisite, not something a successful build proves. No DNS, deployment, remote migration or production tracking is performed by this repository change.

## Release verification and rollback

Before release, exercise separate-browser contexts on both origins with synthetic users. Confirm public-to-private navigation produces a new document; storefront requests to private APIs return 404, unknown hosts return 421, and tracked-origin requests to commerce APIs return 403 without CORS. Confirm account/session endpoints and saved addresses never appear in public network responses, HTML or storage. Check private CSP blocks an injected Meta loader while Airwallex hosted launch, callback and authorized status polling still operate in sandbox. Verify direct checkout, new tabs, login cart merging, selected checkout, Buy now, locale switching and historical product links.

Keep all marketing enablement and readiness switches off during origin rollout. Only enable separately approved pages after the consent/policy and Events Manager checks in the tracking runbook pass. The application kill switch stops new dispatch but cannot recall requests already sent; already loaded SDK code requires a clean document transition.

Rollback disables marketing at runtime first, then restores the previous application build and reverse-proxy routing without moving cookies. Preserve the untracked legacy commerce hostname and payment return/webhook endpoints throughout. Do not remove additive outbox/consent tables during rollback, and do not reset production data.

## Repeatable local browser check

`scripts/test-commerce-isolation.mts` runs a production build against an explicitly supplied, already migrated disposable PostgreSQL database. It refuses every database except `bangbuy_tracking_test` on loopback ports 15439 or 56543. It seeds only synthetic fixture records, starts its own loopback Next process and a temporary TLS reverse proxy, runs Chrome through both configured hostnames, and stops its processes in `finally`. Its generated certificate and screenshots remain in the task temporary directory. It never changes DNS or production infrastructure and disables all marketing/payment delivery flags. The [current staging report](deployment-staging-verification.md) separates a fresh run from earlier results; the [customer-state migration runbook](customer-state-migration.md) documents the unresolved apex/`www` compatibility blocker.

```sh
COMMERCE_ISOLATION_TEST_DATABASE_URL=postgresql://bangbuy_tracking_test@127.0.0.1:15439/bangbuy_tracking_test \
COMMERCE_ISOLATION_REPORT_PATH=/tmp/bangbuy-commerce-isolation-report.json \
npx tsx scripts/test-commerce-isolation.mts
```

The final 10 November 2026 rerun reused the current production build and passed twenty-three recorded checks: thirteen customer journey/isolation checks and ten shared GET-only health checks. These cover policy availability/disabled channels, private headers, host/API isolation, a fresh document on handoff, public option and quantity recovery, guest Buy now preserving the cart, scoped guest receipts, selected-cart checkout, account login merging, registered full-cart checkout, historical slug navigation, Bengali language switching, failed cross-origin private reads, forged payment return parameters and zero external marketing requests. This validates the synthetic local commerce journey; it does not validate a real provider payment, the dual-legacy-host migration, Events Manager acceptance or live conversion delivery.
